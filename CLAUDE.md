# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

PHP Docker images (`ecommpro/php` on Docker Hub) for Laravel, Magento 1/2 and WordPress. PHP is
compiled from the vendored official docker-library recipe; a complete extension catalog is added on
top. One image per branch: `CMD php-fpm`, plus Composer 2, git, unzip and `idle` (keeps a worker
container alive) for everything that is not FPM. No application tooling, no shell customization,
no opinion about uid or HOME (`COMPOSER_HOME=/tmp/composer`, `WORKDIR /app`).

Policy (see README "What you get"): images track the latest stable PHP patch and extension
versions; only `X.Y` and `X.Y.Z` tags exist (`-fpm`/`-cli` are transitional aliases of the same
image); consumers who need pins build their own image or pin a digest. Builds happen when PHP
publishes a patch release.

Each branch is four layers, declared in `versions.php`: system base (Debian + docker-library
recipe commit), origin (php.net tarball), patches (our choice, with provenance; Sury series on
EOL branches 7.3/7.4/8.0/8.1) and extensions (resolved to latest stable compatible at build).

## Commands

All PHP tooling runs in containers (`sudo -n nerdctl`; set `CONTAINER_ENGINE=docker USE_SUDO=0`
for Docker). Builds take 10-25 minutes per branch from scratch; the user prefers to run them.

```bash
./build.sh 8.4                 # generate build/8.4/Dockerfile, build, verify, tag locally; never pushes
./build-all.sh                 # every branch; results under build/runs/<run-id>/
./publish.py [8.4 ...]         # push version + branch tags, verify digests, write releases/*.json
./vendor-php.py 8.4 [--update] # materialize upstream/8.4/ from versions.php (--update: latest docker-library recipe)
./vendor-php.py --all

# generator only / regression test, inside the generator container
sudo nerdctl run --rm -u "$(id -u):$(id -g)" -v "$PWD:/work" -w /work php:8.2-cli \
  sh -c 'PHP_BRANCH=8.4 php build.php && php test-generator.php'   # needs network (PECL metadata)
```

## Architecture

- `versions.php`: per branch `php`, `recipe` (docker-library commit, Debian, optional recipe
  `variant`) and optional `patches` (vendor, package, sha256, selection rules `from`/`also`/`skip`).
- `upstream/<branch>/`: generated by `vendor-php.py`, never edited: official Dockerfile and
  helpers (`SOURCE`), and with patches also `patches/` + `series`, `patches.json` and a Dockerfile
  adapted to apply the series, repack the source and build on the configured Debian.
- `extensions.php` (+ `extensions.legacy.php` for PHP 7): ordered catalog. `extensions/<name>` is
  the base recipe, `extensions/<name>:X.Y` applies to PHP ≥ X.Y (highest match wins), empty file =
  not available. Recipes are shell fragments joined with `&&`.
  - PHP ≥ 8.1: `$PIE_INSTALL vendor/package [--configure-options]`; PIE is bind-mounted from
    `ghcr.io/php/pie:<version>-bin` (version pinned in `build.php`). Disabled-by-default modules
    pass `--skip-enable-extension`.
  - PHP ≤ 8.0: `pecl install name`; `build.php` resolves the latest compatible stable release from
    PECL REST metadata (network needed) and pins it. On PHP 7 it downloads the archive over HTTPS
    first because the old PECL client fails on channel metadata.
- `build.php` + `layout.dockerfile`: generate `build/<branch>/Dockerfile` (stages `php-base`,
  `pie`, `extensions`, final `image`; one cached `RUN` per recipe with shared ccache) and
  `build/<branch>/manifest.json`. The upstream `FROM` becomes `php-base` with an
  `APT_REFRESH`-keyed `apt-get upgrade`. The final `image` stage starts from the same Debian image,
  installs only the packages listed by `mark-runtime-dependencies` (`apt-mark showmanual` minus
  `$PHPIZE_DEPS`/ccache) and copies `/usr/local` from the build: no toolchain in the image, and
  modules are stripped inside their own recipe layer (stripping later would not shrink anything).
  Composer's current stable release is resolved from getcomposer.org at generation time and
  verified by checksum in the Dockerfile.
- `files/image-manifest.php` runs at the end of the build: loads every `.so` in isolation and
  writes `/usr/local/share/php-image-manifest.json` (PHP, source, patches, extension versions,
  enabled-by-default list). A module that does not load fails the build.
- `verify-image.php`, `verify-fpm.php`, `verify-legacy-security.php`: run by `build.sh` inside
  the built image (catalog vs manifest and GD formats; real FastCGI request; OOM worker
  replacement on patched branches). `mark-runtime-dependencies.sh` keeps shared libraries needed
  by compiled modules before `autoremove`.
- `files/idle`: the worker keep-alive script (exits on TERM/INT/QUIT). `files/prepend.*`,
  `xhprof.ini`, `xhproxy.php`: PHP defaults copied into the image.
- `releases/<php>.json`: record of every published image (manifest + digest + tags); the
  `<php>-fpm/-cli.json` files are the pre-merge records of 2026-10-27.
  `build/` is generated and gitignored.

## Conventions

- Never edit `build/`; change recipes, layout or generator and regenerate.
- Keep PIE pinned; never add tags beyond `X.Y` and `X.Y.Z`; never edit `upstream/` or `build/`.
- Do not add application tooling, shells or home/uid conventions to the image; consumers extend it.
- A new PHP branch: add it to `versions.php` (php, recipe commit, Debian), `vendor-php.py`, check
  `extensions/` for needed `:X.Y` variants, run the generator test, then `build.sh`.
